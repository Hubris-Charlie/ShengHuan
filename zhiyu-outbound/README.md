# 智语外呼 · 京东 POP 资质审核驳回外呼数字员工

场景来自赛方真实业务数据：**京东商城品牌入驻资质审核驳回外呼**。
通话结构是四段式：**① 自报身份 → ② 确认对方身份 → ③ 说明驳回原因 + 整改动作 → ④ 礼貌结束**。

> 设计取舍：核心逻辑**零第三方依赖**（纯标准库），音频通路只依赖 `websockets`。
> 这样在 Python 3.14 这类新环境上也能立刻跑起来。

## 一、关单方式判定：先决定该不该打

业务规则来自主表「关单总原则」四条，实现为纯函数 `policy.decide_call()`。
**判定顺序不可调换**，因为规则 3、4 是压倒性的：

| 顺序 | 条件 | 结果 |
|---|---|---|
| 1 | 存在越级投诉 / 外部曝光风险 | **必须回电** + 升级处理 |
| 2 | 商家主动要求回电 | **必须回电**（即使场景是京麦驳回） |
| 3 | 相同场景三次及以上提交错误 | 一律京麦驳回 |
| 4 | 关单方式为京麦驳回 | 不强制回电 |
| 5 | 电话场景 + 二次提交仍错 + 上次未接通 | 创事件 + 预约二次外呼 |
| 6 | 电话场景 + 首次未接通 | 京麦驳回告知原因即可 |
| 7 | 其余电话场景 | 正常外呼 |

规则 1、2 必须排在最前：一个已经威胁要曝光的商家，即使他的驳回场景本身是"京麦驳回"，
也必须打电话。这是业务红线，不是优化项。

## 二、状态机：四段式 + 身份确认硬闸门

| 状态 | 职责 | 关键约束 |
|---|---|---|
| `OPENING` | 自报身份（京东商家资质审核专员）并询问对方是否为申请单上的商家 | 必说：自报身份 + "您是…吗" |
| `VERIFY_MERCHANT` | 等待确认 | ★ **硬闸门**：不确认绝不讲驳回原因 |
| `REJECT_REASON` | 说明具体哪一项不合格 | 必说：驳回原因 |
| `RECTIFY` | 给出可执行的整改动作 | 必说：整改动作 |
| `CLOSE` | 礼貌结束 + 告知热线 4006180092 | 必说：感谢接听 + 热线 |
| `OBJECTION` | 商家质疑（我这明明是真的授权 / 品牌方模板改不了），回应后回原流程 | 不得承诺审核结果 |
| `ESCALATE` | 越级投诉 / 外部曝光 → 升级处理 | 必说：已记录 + 同事跟进 |
| `HANDOFF` | 转人工 | 必说：转接 |
| `EXCEPTION` | 异常兜底 | — |

**为什么身份确认是硬闸门**：给错人讲驳回原因是重大事故（暴露了别家公司的审核信息）。
所以 `VERIFY_MERCHANT` 追问用尽时**不强制推进**，而是礼貌挂断——由 `StateSpec.on_exhaust` 控制：

```python
State.VERIFY_MERCHANT: StateSpec(
    required_slots=("merchant_confirmed",),
    on_exhaust=State.CLOSE,        # ★ 追问用尽 → 挂断，而不是讲驳回原因
    exhaust_reason="unverified_close",
)
```

其他状态追问用尽则允许强制推进（`on_exhaust=None`），保证电话不会卡死。

## 四、话术配置（`config/scripts.json`）

全部多句轮转，同一状态不会连续说同一句。**固定话术 84 句**，另有 68 个场景各自的原因/整改内容。

| 桶 | 用途 | 句数 |
|---|---|---|
| `utterances` | 流程正常推进的正式发言（9 个状态） | 34 |
| `rectify_templates` | 整改动作模板，按句子形态分三个桶 | 10 |
| `reprompts` | 没听清 / 没拿到关键信息时的追问 | 13 |
| `fallbacks` | 超时 / 被合规拦截 / 强制推进时的保底 | 21 |
| `special` | 专用转场（打错人、身份未确认的结束语） | 4 |
| `filler` | 调工具时填空 | 2 |

### 驳回原因与整改动作是「按场景生成」的

这两个不是写死的话术，而是由 `config/scenarios.json` + `config/reason_action.json` 动态算出来的：

- **驳回原因** ← 该场景的二级分类，去掉括号补充说明后直接念
  （`授权书内容不完整（包含盖章…）` → `授权书内容不完整`）
- **整改动作** ← 优先从该场景的**官方参考话术**里拆出整改那句；
  拆不出（带 `【】` 占位符）才退到一级分类的兜底说法

所以 68 个场景各有自己的原因/整改说法，合计 **100 组场景化内容**，不是一套话术套所有。

### rectify_templates 的三个桶

整改动作的句子形态不一样，套同一个模板会出病句，所以分三档：

| 桶 | 适用 | 示例 |
|---|---|---|
| `needs_submit` | 动作是裸动词短语 | `需要您提供在有效期内的注册商标，然后重新提交。` |
| `self_contained` | 动作本身已含"提交" | `请您补齐后重新提交。` |
| `as_is` | 没有自助修改方式 | `暂无自助修改方式，请您联系对接的采销沟通。` |

### 占位符

两套都支持：`{hotline}` / `{role}` / `{工号}`，以及 `【品牌】【类目】【驳回原因】【整改动作】【商家】`。

### 改完必须跑自检

```powershell
python -m unittest tests.test_scripts_config -v
```

逐句检查：**不踩禁语**、**必说话术全覆盖**、占位符合法、热线常量为 4006180092。
注意它校验前会**先渲染占位符**——拿原始模板直接匹配关键词必然误判。

## 五、语音识别三种模式

页面左侧「识别模式」下拉，切换即生效：

| 模式 | 说明 | 需要 |
|---|---|---|
| **浏览器识别**（默认） | Web Speech API 实时识别普通话 | Chrome/Edge + 麦克风权限，零密钥 |
| **服务端识别** | 整句 PCM 送服务端，走 `providers.asr.kind` | `ASR_API_KEY` + `kind: "http"` |
| **脚本台词** | 不看你说什么，按演示脚本吐台词 | 无 |

服务端识别接任意 **OpenAI 兼容 `/audio/transcriptions`**：热词以 `prompt` 传入，这就是领域词表定制的落点。

页面还有**麦克风电平条**和**录 3 秒并回放自检**，用于区分"麦克风没收到"和"收到了没识别"。

## 六、时延口径

**首字响应 = 用户说话结束 → Agent 音频真正开始播放**（`t_playout_start - t_speech_end`）。

两个坑：
1. 不能用 `t_tts_first_byte` 代替 `t_playout_start` —— 抖动缓冲和播放缓冲也是延迟
2. 打断时"已经说到哪儿了"必须按**播放进度**算，不能按**生成进度**算

当前（mock 模拟时延）：**P50 790ms / P95 1033ms**，距 2 秒门槛有充足余量。

## 八、已知限制

- Mock TTS 输出的是占位音（正弦波），不是语音；只为把通路和打断跑实
- 时延为**模拟参数**，报告标 `latency_source: mock_simulated`，接真实服务后自动变 `measured`
- NLU 是规则版（关键词），可替换为 LLM，接口不变
- 话术里的 `【商家】` 未注入真实商家名时显示为 `（商家公司名/店铺名称）`
- 「品牌方不认可授权」两个场景在原始数据里没有话术，当前走 `reason_fallback`
